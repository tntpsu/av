## TOP 3 PROCESS IMPROVEMENTS

```
════════════════════════════════════════════════════════════════
1. Physics-first design checklist at feature start

   Pattern: Proxy approximation is the #1 sub-category (33% of
            design issues). All 3 were cases where a computable
            physical quantity (κ×v², time-to-curve, forward
            velocity profile) was replaced by a hand-tuned proxy.

   Action:  Add a 3-question physics-first checklist to the
            design phase of any new control/planning parameter:
            (a) What physical quantity does this approximate?
            (b) Can we compute it directly from state?
            (c) If using a proxy, what is its error bound at the
                operating envelope boundary?
            Block feature start if (b) is "yes" and (c) is ">5%".

   Impact:  Would have prevented 3 entries outright (entries 2, 9,
            12). Collectively those recovered +98 points across 10
            track-runs and eliminated 3 per-track overlay workarounds.

────────────────────────────────────────────────────────────────
2. Pre-merge E2E gate for any numeric constant change in
   config/av_stack_config.yaml or _MPC_WEIGHT_AUTO_DERIVE_PARAMS

   Pattern: Entry 13 (mpc_q_lat revert) cost +82.5 points across
            4 tracks because an undocumented 2-line tuning change
            was bundled into a feature commit that explicitly
            deferred E2E validation. Detection required 1 bisection
            iteration but only because /iterate was used manually.

   Action:  Nightly sweep already gates on scores. Add a pre-commit
            check: if git diff HEAD touches any numeric literal in
            the scoring-critical params list (tools/ci/
            check_config_regression.py --critical-only), require
            the commit message to contain "E2E-validated: <run-id>"
            or block. The existing config regression CI check
            already exists; route its output through a gate rather
            than informational only.

   Impact:  Entry 13 would have been prevented entirely. Also
            closes the undocumented-tuning-in-feature-commit
            pattern that /iterate catches at cost (3+ bisect runs).

────────────────────────────────────────────────────────────────
3. Temporal-domain review for any distance-based threshold
   in a speed-varying system

   Pattern: Two separate entries (5: control rate coupled to
            perception rate; 10: distance-proxy-for-time entry
            arm) were caused by conflating distance with time. In
            a speed-varying system, distance thresholds express
            inconsistent time windows across the operating range.

   Action:  Add a design-review rule: any threshold expressed in
            meters that gates behavior affecting steering or speed
            must include a time-domain analysis showing the
            behavior is acceptable at v_min and v_max. Concretely:
            a comment or test asserting `threshold_m / v_min` and
            `threshold_m / v_max` are both within the intended
            window. For control-loop rates, assert control_hz >=
            2× perception_hz in the system integration test.

   Impact:  Would have caught entries 5 and 10 at design time
            (detection_delay 4 and 1 respectively). Entry 5 alone
            required 4 iterations before root cause was isolated.
════════════════════════════════════════════════════════════════
```
